# V4 Run 089 — Controlled Physical Resumable Acceptance Mode

## Starting point

This run continued from V4 Run 088 on branch `v4`. Branch `v3` was inspected before work and was not modified.

Run 088 had already built the durable server-authoritative resumable ledger and acceptance ingestion composition, but normal Desktop startup did not provide a production authority configuration, so the acceptance endpoint intentionally remained unavailable.

## Implemented

### Explicit production acceptance mode

`createResumableMediaProductionRuntime()` now resolves a controlled production mode directly from the Desktop process environment:

- normal runtime remains disabled when `PHOTOX_PHYSICAL_RESUMABLE_ACCEPTANCE_MODE` is absent;
- the only accepted mode is `real-device`;
- enabling it requires `PHOTOX_RELEASE_COMMIT_SHA` to be an exact 40-hex commit SHA;
- invalid mode, invalid/missing release SHA, or missing workspace usage authority fails closed during composition rather than silently weakening acceptance requirements.

No renderer/Desktop/Web toggle was added. This remains release/test tooling, not a normal operator switch.

### Server-authoritative quota and catalog counters

When controlled mode is enabled, the server authority derives its evidence independently from existing production authorities:

- quota bytes come from the active workspace repository `managedStorageBytes` authority;
- catalog observation comes from the active media catalog `exists({ workspaceId, key })` authority for the exact `deviceId:assetId` identity;
- the server records a catalog row value of `0` or `1` for that target identity before and after the resumable run;
- timestamps are generated by the Desktop runtime;
- mobile still cannot provide authoritative offset, quota, catalog, verification, or duplicate-side-effect values.

The authority counter source now receives the bound resumable session, so the catalog observation is tied to the exact authenticated workspace/device/asset/session rather than a client-selected catalog identity.

### Exact release binding

`PhysicalResumableAcceptanceIngestion` now optionally receives the configured release commit SHA. In controlled production mode it rejects a mobile artifact whose `release.commitSha` does not match that exact Desktop release before consulting the server authority or writing evidence.

This closes a gap where otherwise-valid observations from another build could have been appended to the current run's evidence store.
